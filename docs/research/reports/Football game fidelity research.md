# Build the simulation first, then the feel

Nobody outside EA and Konami has shipped gameplay at EA Sports FC fidelity. EA gets there with full-match motion capture (Xsens suits plus positional tracking in FIFA 22, volumetric video from 180+ real matches in FC 24), machine-learned ball-approach animation, and libraries of more than 11,000 animations. A solo, agent-driven Unity project cannot reproduce that, and it does not need to. The studios that came closest on small budgets (Rematch, Sociable Soccer, Football Manager 26's Unity presentation) won on a different axis: a responsive, carefully tuned ball, and a deterministic simulation kept separate from presentation. OpenFifa should take that route. It should grow its 4v4 Rush mode into a fixed-step C# match simulation (ball physics, rules, utility AI on a pitch-control grid), driven at about 10 Hz for decisions and 120–240 Hz for the ball. Animation should follow the simulation through MIT-licensed motion matching, root-motion warping and foot/ball IK. Commentary should be a stitched, pre-rendered TTS bank. Gamepad controls should use the FC "Classic" functional layout, and touch should use a floating stick with context-relabelled buttons. Two of the owner's assumptions need to change. First, bundling EA FC 27 ratings scraped from sofifa, together with real Premier League clubs, is the single biggest legal and App Store risk in the plan. The safe pattern is fact-only squads from CC0 sources, OpenFifa's own derived ratings, and a user import format. Second, the iPad pipeline extends ios-factory cleanly only if two pins hold: Unity exports the Xcode project on Linux with Unity 6000.3.8f1 or later, and the `macos-26` runner compiles and uploads it with Xcode 26. Each TestFlight build costs roughly $1.50 of macOS minutes.

## Nobody outside EA ships FC fidelity, and reviewers judge the ball and the keeper first

The most complete open football simulator is still Google Research Football (GRF), a heavily customised fork of Bastiaan Konings Schuiling's C++ "Gameplay Football". GRF is **Apache-2.0** and its parent repository is under the **Unlicense** ([GitHub](https://github.com/google-research/football); [GitHub API](https://api.github.com/repos/BazkieBumpercar/GameplayFootball)), but GRF was **archived on 19 August 2026**. Porting C++/SDL/OpenGL code to Unity C# would be a rewrite, so GRF's value to OpenFifa lies in its design, not its code. It simulates the full rule set (fouls, cards, offside, handball, set pieces, fatigue). Agents and humans share one interface of **one action per 100 ms**. The rule-based opponent has a single difficulty scalar θ (easy 0.05, medium 0.6, hard 0.95), and non-active teammates run on a separate rule-based bot. The game has stochastic and deterministic modes ([Kurach et al.](https://ar5iv.labs.arxiv.org/html/1907.11180)). One detail is a direct warning for OpenFifa: the maintainers **removed the "switch active player" action because learned policies exploited it**. Player switching is an exploit surface and needs explicit rules.

Outside GRF, no permissively licensed 11v11 Unity football game exists. What is out there is small: 2D prototypes, a GPL-3.0 arcade game with behaviour trees ([FutbolSim](https://github.com/Dubium0/FutbolSim)), and ML-Agents 2v2 experiments. The commercial record points to a less obvious conclusion: **engine choice barely predicts feel**. eFootball moved from Fox Engine to Unreal Engine 4. eFootball 2022 became Metacritic's worst-reviewed game of 2021, even though it had four times more animations than earlier PES games ([VGC](https://www.videogameschronicle.com/news/konami-insists-its-taking-criticism-of-efootball-very-seriously-ahead-of-big-update)). UFL, on Unreal Engine 5, drew complaints that players "move robotic", along with criticism of its goalkeepers and balance ([SGO](https://www.sportsgamersonline.com/games/soccer/ufl-review-a-solid-foundation/amp/); [OpenCritic](https://opencritic.com/game/17857/-)). Sloclap's Rematch went the other way. Director Pierre Tarno calls the ball "the basic brick of the game". The team treats bounce height and curve as muscle-memory-sensitive parameters and caps kick speed so that defenders and keepers can still react, trading realism for flow ([Console & PC Gaming](https://consolepcgaming.com/how-rematch-developers-balance-the-balls-feel-and-function-in-gameplay)).

Two precedents match OpenFifa's situation closely. **Football Manager 26 moved its rendering to Unity while keeping its match-engine logic proprietary**, and critics praised that match engine even as they panned the UI ([Wikipedia](https://en.wikipedia.org/wiki/Football_Manager_26); [PC Gamer](https://www.pcgamer.com/games/sports/football-manager-26-review)). That is exactly the simulation/presentation split OpenFifa should adopt. **Sociable Soccer**, Jon Hare's Sensible Soccer successor, is built in Unity, was designed from day one for both touch and controller, and shipped on Apple Arcade ([Pocket Gamer](https://www.pocketgamer.com/sociable-soccer/an-interview-with-jon-hare-on-sociable-soccer-apple-arcade-and-how-his-team-made)). It is the nearest public proof that this platform combination works. Across these games the order of punishment is consistent. Reviewers forgive visuals that fall short of EA. They do not forgive robotic movement, weak goalkeepers, or a ball that feels wrong.

## Simulation first, animation follows: the stack a small team can actually build

### What EA has published, and how much of it transfers

EA's public technical record is thin: one GDC talk and a run of marketing "Pitch Notes". The GDC 2022 Animation Summit talk describes a 90-minute, 11v11 capture recorded with **Xsens inertial suits, a local positioning system and static cameras**. EA used that capture to improve athleticism and ball-physics realism, and to train **ML-Flow, "a machine-learned procedural animation system"** ([GDC Vault](https://gdcvault.com/play/1027595/Animation-Summit-FIFA-22-s)). ML-Flow was trained on about **8.7 million frames** and generates the ball approach at runtime: stride adjustment, cadence and pose matching ([EA Pitch Notes FIFA 22](https://www.ea.com/ea-play/news/pitch-notes-fifa-22-gameplay-deep-dive)). FC 24's HyperMotionV switched to volumetric video from **180+ professional matches**, reaching **11,000+ animations** and 1,200+ signature run styles ([EA Pitch Notes FC 24](https://www.ea.com/games/ea-sports-fc/pitch-notes/news/fc-24-gameplay-deepdive)). The FC 26 notes are the most useful to an indie team, because they show what EA is still fighting. EA normalised animation speed by player height, reworked foot-preference logic and animation branching, cut "locked-in animation" feel, went back to three acceleration types, and gave players far from the ball relaxed "low-urgency" locomotion ([EA Pitch Notes FC 26](https://www.ea.com/games/ea-sports-fc/fc-26/news/pitch-notes-fc26-gameplay-deep-dive)). Taken together, these changes describe a game that is **simulation-first with animation following**: attributes drive a gameplay capsule, and animation is warped to keep up with it. The older GDC talk "Animation Warping for Responsiveness in FIFA Soccer" says the same thing directly. Turn animations are procedurally altered to reach a target point at a target time, and **warping beats blending for responsiveness** ([GDC Vault](https://gdcvault.com/play/1012342/Animation-Warping-for-Responsiveness-in)).

On the tactical side, EA's FC IQ (FC 25) replaced work rates with Player Roles, Team Tactics and Smart Tactics. The only published use of ML in FC IQ is a model fed by Opta data that assigns role familiarity, not one that makes runtime decisions ([EA FC IQ deep dive](https://www.ea.com/fr-fr/games/ea-sports-fc/fc-25/news/pitch-notes-fc-25-fc-iq-deep-dive)). Positioning in commercial football games is formation-relative and role-driven, and is not learned end to end.

### Motion matching is the realistic animation core, and Unity does not supply one

Motion matching is a nearest-neighbour search over pose and trajectory features in a mocap database, followed by inertialised blending. Ubisoft introduced it (Clavet, GDC 2016) and it is now standard in AAA games. Learned Motion Matching later cut its memory footprint by replacing each stage with a neural network ([Ubisoft La Forge](https://www.ubisoft.com/en-us/studio/laforge/news/3NWqwcMU9lMfumgfPAEfka/learned-motion-matching)). Sebastian Starke's neural controllers are closer to football than anything else published. Local Motion Phases, built with EA, gives each limb its own phase so the network learns ball contact, and was demonstrated on 1v1 basketball dribbling. The AI4Animation code, however, is **licensed for research or education only, with mocap data under CC BY-NC 4.0** ([AI4Animation](https://github.com/sebastianstarke/AI4Animation)). OpenFifa can borrow the idea and add a per-foot "time to next ball touch" feature to its motion-matching feature vector, but it cannot ship the code.

Unity is no help here. **Kinematica is deprecated** and never left preview ([Unity docs](https://docs.unity3d.com/2020.2/Documentation/Manual/com.unity.kinematica.html)). A secondary source reports that Unity **paused new animation-system work to prioritise CoreCLR** ([Digital Production](https://digitalproduction.com/2025/11/26/unitys-2026-roadmap-coreclr-verified-packages-fewer-surprises/)). A 2027 roadmap should not depend on it. The table below lists the practical tools.

| Need | Recommended tool | Licence / cost | Why |
|---|---|---|---|
| Locomotion | [JLPM22/MotionMatching](https://github.com/JLPM22/MotionMatching) | MIT, Unity 6+ | Trajectory prediction, drift clamping, inertialisation and foot locking. Research-backed (SIGGRAPH Asia 2025). Work in progress. |
| Locomotion (alternative) | [MxM fork, Frost-Blade Studios](https://motion-matching-for-unity.readthedocs.io/en/latest/getting-started/) | Formerly commercial, now open source. Check the LICENSE file. | More mature tooling, tested on Unity 6 |
| Foot/ball IK | Animation Rigging | Free | Two-bone IK and aim constraints on Animation Jobs |
| Full-body IK, tackles | [Final IK](https://assetstore.unity.com/packages/tools/animation/14290) + PuppetMaster | About $90 each | Grounder, full-body IK, active ragdoll for challenges |
| Action clips | [AA Soccer Player Animations](https://marketplace.unity.com/packages/3d/animations/aa-soccer-player-animations-package-237656) | About $68, 135 clips | Kicks, falls, throw-ins |
| Offline ML | [ML-Agents 4.x / Sentis](https://docs.unity3d.com/Packages/com.unity.ml-agents@4.1/manual/Inference-Engine.html) | Free | Use for tuning experiments only. CPU (Burst) inference beats GPU for small models. |

The catch is data. Motion matching needs long, unstructured locomotion "dance card" takes (jogs, sprints, cuts, turns on the ball, shielding). Asset Store packs are short loops and actions, so they only partly feed a motion-matching database. The gap is cheapest to close with markerless video capture of a single isolated actor. Commercial use requires a paid tier: **Move.ai's $15 Personal plan is non-commercial, and commercial use starts at Standard, $50/month** ([aitoolsatlas](https://aitoolsatlas.ai/tools/move-ai/pricing), secondary source).

### Ball, contact and team AI are code problems, which suits agents

No shipped football game has published its ball model, so the coefficients that follow are standard approximations rather than sourced figures. A credible ball needs gravity, quadratic drag (Cd of about 0.2–0.25 above the drag crisis and about 0.45 below it, with m ≈ 0.43 kg and r ≈ 0.11 m), a Magnus term F = S(ω × v) tuned so a 25 m/s free kick curves 2–4 m, exponential spin decay, and a bounce model with restitution of about 0.6–0.8 that couples spin to velocity. OpenFifa should integrate the ball itself, with semi-implicit Euler or RK4 at 120–240 Hz, and not through PhysX. A custom integrator gives determinism for replays and tests, cheap time-to-intercept prediction for the AI, and analytic pass and shot solving. Every game layers assistance on top of the physics. Passes solve launch velocity toward a lead point. Shots choose an aim point inside an error cone set by attributes. Dribbling drives the ball kinematically between touches and fires each touch impulse from the contact-frame animation event. The community lists the pitfalls of this approach as **foot "sliding and skating"** and players who "plop" toward the ball before each touch ([Unity Discussions](https://discussions.unity.com/t/procedural-character-animation-soccer/769433)). The fix is to cap the ball "magnetism" so that dribble speed never exceeds the animation's natural speed.

For off-ball AI, the best-documented quantitative model is **pitch control**: Spearman's physics-based time-to-intercept model, and Fernández and Bornn's velocity-dependent influence model ([Barça Innovation Hub](https://elearning.barcainnovationhub.com/the-science-of-space-creation/); [Frontiers review](https://www.frontiersin.org/articles/10.3389/fspor.2021.676179)). Open Python teaching implementations exist ([Soccermatics](https://soccermatics.readthedocs.io/en/latest/_sources/lesson6/PassProbability.md.txt)). On a 32×20 grid with 22 players, pitch control is about 14,000 evaluations per update, trivial in Burst at 5–10 Hz. The AI should have four layers. A team-phase state machine sits on top (build-up, transition, settled attack, press, low block). Below it, formation anchors shift and compress with the ball, in the style of FC IQ. Below that, a per-player utility scorer weighs passes, runs, presses and covers against pitch-control values and interception probability. At the bottom, steering feeds the motion-matching trajectory. Reinforcement learning has no commercial precedent for full-team control. It is useful at most for narrow sub-skills such as goalkeeper positioning.

### iPad budget: about 25 skinned characters is tractable with animation LOD

No primary benchmark exists for 22 skinned players on iPad, so the numbers below are engineering estimates to validate early. They are about 15–25k triangles per player at LOD0, GPU skinning on Metal, and a motion-matching search every 3–6 frames, staggered across players. Full IK runs only near the ball. Distant players fall back to cheap blend trees, the same idea as EA's "low-urgency" animations. The crowd uses GPU-instanced impostors or vertex-animation textures and never skinned meshes. The frame target is 60 fps on M1/A15-class hardware with about 12 ms of headroom.

## Stitched clips beat live LLMs for commentary, and FC Classic sets the button layout

### Commentary: copy EA's event-tagged, priority-gated stitcher

FIFA commentary is thousands of short **ad-libbed** clips, not scripted lines. EA found scripted lines "weren't very good" because commentators "are not actors". A rules-based commentary AI selects lines from objective event parameters (score, pitch position, shot velocity). Many lines play only when crowd intensity is below a threshold, but resolution lines such as "wide" pre-empt everything else. EA's audio director names stitching as the hardest problem ([Designing Sound](https://designingsound.org/2013/02/spectral-analysis-interview-with-jeff-macpherson/)). Names are the scaling bottleneck. **FC 26 has 20,000+ player names**, each recorded in several tones, and EA now uses an AI clone of Guy Mowbray's voice **with his permission** for some of them. Mowbray says each longer line has about ten phrasings ([PCGamesN](https://www.pcgamesn.com/ea-sports-fc-26/ai-commentary-lines-guy-mowbray)).

Live LLM play-by-play fails on latency. Research on game commentary identifies the sequential text-then-speech pipeline as the bottleneck. One system works around it by deliberately delaying the video ([IJCAI 2026](https://arxiv.org/pdf/2606.13322)). Another finds that predicting events ahead of time "significantly reduces response latency" ([MDPI Mathematics](https://www.mdpi.com/2227-7390/13/17/2738)). Possession changes every one to two seconds, so live play-by-play needs well under 500 ms from event to audio, and cloud LLM plus TTS over mobile networks does not meet that. Cost is not the constraint. A bank of about 3,000 event lines for two voices, plus about 2,000 names in three intonations, comes to roughly 450K characters. That costs about $18–36 at ElevenLabs' current **$0.04–0.08 per 1K characters** ([ElevenLabs](https://elevenlabs.io/pricing/api)). **Kokoro-82M is Apache-2.0, about 80 MB in INT8, and runs on the Apple Neural Engine on iOS 18+** ([soniqo](https://soniqo.audio/guides/kokoro)), which makes fully offline or on-device generation free. The recommended design has four parts. A pre-rendered bank covers play-by-play and colour. Names come in neutral, rising and resolving intonations. Each line carries a priority and an interruptible flag, with per-line cooldowns. Optional LLM-written colour lines play only in dead-ball windows. Two hard rules apply: **never clone a real commentator's voice**, and disclose AI-generated audio in store metadata, as EA did. Crowd audio should copy EA's layering: an intensity-graded murmur bed, reaction one-shots, "salt and pepper" callouts, panned home and away sections, and dynamics shaped to avoid fatigue. A single `CrowdIntensity` parameter driven by xG and the scoreline can control it. FMOD and Wwise both have free indie tiers (Wwise is free under a $250K budget; [Audiokinetic](https://blog.audiokinetic.com/en/wwise-licensing-and-pricing-philosophy/)), and Unity's AudioMixer is enough for a first version.

### Controls: FC Classic on gamepad, context-relabelled buttons on glass

FC 26 has four control presets (Classic, Alternate, Two Button, One Button). Classic is the muscle-memory standard ([FIFPlay](https://www.fifplay.com/fc-26-controls/)). eFootball swaps shoot and lofted pass ([GamingOnPhone](https://gamingonphone.com/guides/efootball-2026-controller-controls-and-button-mapping-guide)).

| Function | FC Classic (PS / Xbox) | OpenFifa default binding |
|---|---|---|
| Ground pass / contain | X / A | `<Gamepad>/buttonSouth` |
| Lob, cross / slide | Square / X | `buttonWest` |
| Through ball / rush GK | Triangle / Y | `buttonNorth` |
| Shoot, tackle, clear | Circle / B | `buttonEast` |
| Sprint | R2 / RT | `rightTrigger` |
| Shield, jockey | L2 / LT | `leftTrigger` |
| Switch player, modifiers | L1 / LB | `leftShoulder` |
| Finesse, call support, team press | R1 / RB | `rightShoulder` |
| Skills, manual switch | Right stick | `rightStick` |
| Quick tactics, subs | D-pad | `dpad` |

US case law treats functional control mappings and mechanics as unprotectable ideas. *Tetris v. Xio* and *Spry Fox v. 6waves* show that copying expressive presentation is what gets a game into trouble ([Mondaq](https://www.mondaq.com/unitedstates/gaming/591564/when-it-comes-to-games-the-practical-limit-to-united-states-copyright-protection-may-only-be-skin-deep); [Eric Goldman](https://blog.ericgoldman.org/?p=10653)). OpenFifa can therefore mirror the FC button map. It should not copy EA's HUD, radar, menu trade dress, or terms like "PlayStyles" and "Ultimate Team". The name "OpenFifa" itself contains a registered trademark and should change before any public release.

On touch, two families dominate. One is a virtual stick with contextual buttons (Dream League Soccer's stick plus three buttons, [App Store](https://apps.apple.com/ng/story/id1494291945)). The other is gestures (FC Mobile's gesture mode and eFootball's "Touch & Flick"). Both games let players mix the two and add assist layers such as eFootball's Smart Assist ([Konami](https://www.konami.com/efootball/en-us/page/new_controls); [EA](https://www.ea.com/ea-studios/ea-sports/news/gameplay-controls-guide-gesture-controls)). On iPad, OpenFifa should use a floating left stick that spawns in the left 40% of the screen, which matters on a 13-inch device. The right cluster should have four buttons: pass (tap ground, hold driven), shoot (hold to charge, swipe to chip or finesse), through, and lob. In defence the same four relabel to switch, tackle, contain and slide. Settings should cover assist level, resize and reposition, and a left-handed mirror. Gamepad support is a real differentiator: **eFootball mobile allows controllers only in AI modes**, and EA has said FC Mobile has no plans for controller support ([EA forums](https://forums.ea.com/discussions/fc-mobile-technical-issues-en/re-can-you-connect-a-controller-to-fc/8051321)). Unity's Input System has iOS classes for DualSense, DualShock 4, Xbox Bluetooth and generic MFi controllers, but it **does not support rumble or lightbar over Bluetooth on iOS** ([Unity Input System](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.4/manual/SupportedDevices.html)). Haptics would need a native `GCController` plugin. Bind to generic `Gamepad` paths, auto-switch `PlayerInput` control schemes, and hide the touch overlay when `onDeviceChange` reports a controller.

## Agents need a deterministic sim, milestone gates and a human for feel

Unity's official agent path changed in 2026. **The Unity CLI (beta) drives the Editor through the `com.unity.pipeline` package**, has an MCP mode, and ships with an **official Claude Code plugin of 29 skills**. The in-Editor MCP server from the paywalled period is deprecated, and Unity says both the CLI and MCP are free ([Unity Discussions](https://discussions.unity.com/t/announcing-the-unity-cli-a-new-way-to-connect-your-tools-and-agents/1731104); [Unity blog](https://unity.com/blog/unity-plugin-for-claude-code); pricing history via a competing vendor, [StraySpark](https://www.strayspark.studio/blog/is-unity-mcp-free-2026)). The community server with the clearest fit for a headless VPS is **IvanMurzak/Unity-MCP** (Apache-2.0). It has an official Docker image, a `-batchmode -nographics` CI example, Linux x64/arm64 server binaries, Roslyn script execution, EditMode/PlayMode test runs, and a runtime mode that works inside a built player ([GitHub](https://github.com/IvanMurzak/Unity-MCP)). CoplayDev's MIT server has the most traction, at about 15k stars ([GitHub](https://github.com/CoplayDev/unity-mcp)). No source confirms that the official `unity mcp` mode controls a Linux batchmode Editor, so the first infrastructure task is to test that on the VPS. With `-nographics` no tool can render, so screenshots need `xvfb-run` with Mesa llvmpipe or lavapipe (documented for other engines, not for Unity) or a WebGL build captured in headless Chromium. Unity Personal also cannot use manual `.alf/.ulf` activation according to Unity's own 6.3 manual ([Unity docs](https://docs.unity3d.com/Manual/ManualActivationCmdWin.html)), which conflicts with GameCI's documentation. The existing CI secrets work today, but the conflict is a fragility to watch.

The best-documented agent-built Unity game is **Mowtopia**, built with Claude Code from a seven-milestone PRD. Each milestone had deliverables, acceptance criteria and a hard stop for human validation. The test count grew at every milestone (15 → 60), and the rules lived in AGENTS.md: "Implement one milestone at a time" and "Do not claim a build has been tested unless it has actually been run". Its real failures were parallel sessions overwriting scenes and prefabs, fixed with an "every file has one owner" rule, and Editor screenshots that misrepresented game state. Browser checks of the web build caught bugs that the tests missed ([Froessell](https://froessell.substack.com/p/how-i-build-a-unity-game-with-claude)). The Unity-Playtest-for-Claude skill adds the right philosophy for a football game. It drives the real Input System bindings, waits on game state rather than timers, never hand-edits `.unity`, `.prefab` or `.meta` files, and holds that "**feel, sound and visuals are never marked passed by a script**" ([GitHub](https://github.com/GhazaGG/Unity-Playtest-for-Claude)). No agent-built Unity football game has been documented. OpenFifa's 821 tests are already ahead of every public case found.

For OpenFifa, this argues strongly for the simulation/presentation split described above. A seeded, fixed-timestep match core with no `Time.deltaTime` lets agents run thousands of bot-vs-bot matches headlessly and assert invariants. Examples are that the ball stays in bounds, offside calls match a geometric oracle, possession and shot statistics fall in plausible bands, and a difficulty θ sweep is monotonic. These runs make AI and physics tuning measurable. Animation quality, ball feel and touch ergonomics stay behind a human-signed gate on a real iPad. Vision-model scoring of captures can be advisory but never pass/fail.

## The sofifa request is the project's largest legal risk

The owner asked for real Premier League players with EA FC 27 ratings from sofifa. The research strongly advises against shipping that. Sofifa mirrors EA's own ratings database of 17,000+ players ([EA](https://ea.com/en/games/ea-sports-fc/ratings/player-ratings/jacopo-petriccione/225381)). It throttles scrapers through Cloudflare ([sofifa-web-scraper](https://github.com/prashantghimire/sofifa-web-scraper)), and even sofifa-derived projects warn that commercial use may breach the site's terms ([crset](https://github.com/uesleibros/crset)). The "CC0" labels on Kaggle FIFA datasets are uploader assertions that cannot override EA's rights ([DagsHub](https://dagshub.com/DagsHub/open-source-ml-datasets/src/main/EA_SPORTS)). In EU and UK law, single numbers are not copyright works. *Football Dataco v Yahoo* held that even fixture lists lack the needed creativity ([SCL](https://www.scl.org/2407-football-dataco-no-database-copyright-protection-for-fixture-lists/)). EA's reviewer network, however, is the kind of investment in obtaining and verifying data that the **sui generis database right** protects. *Football Dataco v Sportradar* treats copying a protected database to users in another member state as re-utilisation ([SCL](https://www.scl.org/2595-database-right-ecj-judgment-in-football-data-co-v-sportradar/)). Quoting one player's rating is harmless. A bundled 500-player Premier League attribute table is a substantial part. The research also could not confirm that FC 27 ratings are on sofifa yet.

The other rights add more exposure. Player names and likenesses are licensed collectively through **FIFPRO**, which has a game-developer intake form but no published indie terms ([FIFPRO](https://www.fifpro.org/who-we-are/commercial)). Clubs hold some players' rights. EA cited its AC Milan agreement in the 2020 Ibrahimović dispute ([Dexerto](https://www.dexerto.com/fifa/ea-sports-responds-to-zlatan-ibrahimovics-fifa-21-licensing-threats-1469512/)). Club crests, kits and league marks are registered trademarks. Even Konami shipped "London FC" and "Manchester B" in PES 2020, with only Arsenal and Manchester United licensed ([GamesAtlas](https://gamesatlas.com/pes-2020/features/pes-2020-all-the-real-names-of-the-unlicensed-teams-and-leagues-of-efootball-pes-2020)). FM26 still ships fake names ([FM Scout](https://www.fmscout.com/a-fm26-real-names-license-fix.html)). Apple's guideline **5.2.1** requires the submitter to own or license the IP, and **5.2.2** requires permission for content taken from third-party services, with "authorization ... provided upon request" ([Apple](https://developer.apple.com/app-store/review/guidelines/)). External TestFlight goes through Beta App Review, so the problem can surface before launch. The encouraging precedent is that **Sociable Soccer, an indie, obtained a FIFPRO licence** ([GamesIndustry.biz mirror](https://dcmpx.remotevs.com/biz/gamesindustry/www/SL/sociable-soccers-jon-hare-says-real-player-names-are-vital-as-studio-secures-fifpro-licence)), and Retro Bowl reached tens of millions of players with no licence at all ([Awful Announcing](https://awfulannouncing.com/gaming/while-ea-fights-over-nfl-licenses-retro-bowl-is-winning-football-gaming-without-one.html)).

The safe pattern has four parts. Ship fictional clubs, original kits and crests, and either fictional players or fact-only squads. Squad facts can come from **Wikidata (CC0)** and fixtures from **openfootball (public domain)** ([Wikidata](https://www.wikidata.org/wiki/Wikidata:Licensing); [openfootball](https://github.com/openfootball/football.json)). Compute OpenFifa's own ratings: take per-90 rates from open or licensed statistics, convert them to percentiles within each position, blend with an editable reputation prior, and use a scale unlike EA's (FM-style 1–20, for example). **Never fit to or sanity-check against EA numbers** in the repo, because that reproduces their database by another route. Publish an open JSON/CSV schema with Files-app import on iPad, the PES option-file model ([GamesRadar](https://gamesradar.com/pes-2021-option-file)). Do not host or link real-IP packs from the official repo or app. Keep a per-field provenance log to answer Apple on request. Private, unshipped TestFlight builds for the owner's internal team are far lower risk than public distribution. Even internally, keep the scraped data out of git, since the repo is the thing most likely to become public. None of this is legal advice. Talk to counsel before any public release, and especially before a rename or licence decision.

## Linux exports, the Mac only compiles: extending ios-factory to Unity

The GameCI-documented pattern fits ios-factory almost exactly. Job one runs `game-ci/unity-builder@v4` with `targetPlatform: iOS` on `ubuntu-latest`, reuses the existing `UNITY_LICENSE`/`UNITY_EMAIL`/`UNITY_PASSWORD` secrets, and uploads `build/iOS` as an artifact. Job two runs on macOS, restores executable bits on `*.sh` and `usymtool*` (the IL2CPP helpers lose them in the artifact), and then archives `Unity-iPhone.xcodeproj` (scheme `Unity-iPhone`) and uploads to TestFlight ([GameCI](https://game.ci/docs/github/deployment/ios)). The macOS job never runs Unity, so it needs no Unity licence, and ios-factory's App Store Connect API-key signing should carry over with `DEVELOPMENT_TEAM` set. Three pins matter. First, use **Xcode 26**: App Store Connect rejects builds from older SDKs ([Unity Build Automation docs](https://docs.unity.com/en-us/build-automation/reference/available-xcode-versions)), and GameCI's sample still shows 16.4. Second, use **Unity 6000.3.8f1 or later** for UIScene lifecycle support, which Apple will require on the post-iOS-26 SDK ([Unity Discussions](https://discussions.unity.com/t/info-apple-update-your-editor-to-receive-uiscene-lifecycle-support/1709065)). Third, set `ITSAppUsesNonExemptEncryption=false` to skip the export-compliance prompt. Set the target device to iPad Only, with landscape orientation and `UIRequiresFullScreen`. ProMotion iPads need no special plist key ([Apple](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays.md)), but measure on device whether `targetFrameRate = 120` actually takes effect.

macOS standard runners cost **$0.062/min and count 10× against included minutes** ([GitHub](https://docs.github.com/en/billing/reference/actions-runner-pricing)). An estimated 25-minute IL2CPP archive therefore costs about $1.55, so 20 builds a month is about $30–35. These timings are unmeasured. Cutting cost means running the Mac job only on tags or `workflow_dispatch`, caching `Il2CppOutputProject` and DerivedData, and using "Faster (smaller) builds" IL2CPP code generation. Codemagic's 500 free M2 minutes could absorb the Xcode stage alone, but running Unity on Codemagic requires a Plus or Pro serial ([Codemagic](https://docs.codemagic.io/yaml-quick-start/building-a-unity-app/)). For testing without a device, a second Linux export with `SimulatorSDK` and `ARM64` builds with `xcodebuild -sdk iphonesimulator`. It can then boot an iPad Pro simulator and capture screenshots and video with `simctl`, mirroring ios-factory's screenshot step. Device and simulator builds are not interchangeable ([Unity Discussions](https://discussions.unity.com/t/exporting-for-ios-simulator-but-with-arm64-arch-impossible/838328)). Simulator frame rates mean nothing, and Metal support on GitHub's virtualised Macs is unconfirmed. Controller logic is best tested on Linux with the Input System's virtual `Gamepad` in `InputTestFixture`. Performance and real controllers need hardware: AWS Device Farm at **$0.17 per device-minute** or Firebase Test Lab's Game Loop at **$5 per device-hour** ([AWS](https://aws.amazon.com/device-farm/pricing); [Firebase](https://firebase.google.com/docs/test-lab/usage-quotas-pricing)). A single owned iPad on TestFlight is still the only real gate for feel.

## Recommended architecture and prioritized roadmap

The architecture has three layers with one-way dependencies. The **match core** is pure C# with no UnityEngine types in its hot paths, so it runs in EditMode tests and batchmode. It holds a fixed-step ball integrator at 120–240 Hz with drag, Magnus, spin decay and bounce, a rules state machine (restarts, offside, fouls, cards), player kinematic capsules driven by attributes and three acceleration types, a decision tick at about 10 Hz, the four-layer AI (team phase, formation anchors, utility scoring over a Burst pitch-control grid, steering), assisted pass and shot solvers, and a seeded RNG with a difficulty θ. The core emits a typed **event stream**: touch, pass, shot, save, foul, restart, goal, each with player ID, zone, xG and speed. The **presentation layer** subscribes to the core and never writes back to it. It covers motion matching with root-motion warping and foot/ball IK, the camera, crowd intensity, and the commentary director, which selects, prioritises and stitches clips from a pre-rendered bank. **Input** maps Input System actions, with a Gamepad scheme on the FC Classic layout and a Touch scheme with context relabelling, into the same intent structs the AI emits. Humans and bots therefore share one interface, as in GRF, and agents can replay recorded intents. **Data** is a versioned JSON schema for teams, players, attributes and ball tuning, filled from CC0 facts plus OpenFifa's own ratings model, with a provenance log and an import path.

| Priority | Milestone | Acceptance gate |

## Conclusion

The research changes how the question should be framed. "FC-level" is not reachable as a content target. EA's moat is capture volume, more than 11,000 animations and licences, and no indie team, agent-driven or not, closes that gap. It is reachable as a **feel** target, and feel turns out to be mostly code: ball tuning, warping, contact timing, AI positioning and responsive input. Code is the part that Claude Code agents with a deterministic, testable core do best. OpenFifa's real advantage is a test culture no public football project has. The highest-leverage move is to point that culture at a simulation which humans and bots drive through the same intents, so that every tuning change can be measured before a person judges the feel on an iPad.

The two decisions that most affect whether the project ships are not technical. Real PL players with EA ratings would put the strongest IP claims in the space (EA's database right, club trademarks and players' image rights) into an App Store submission that must certify ownership. A fictional league with an import path is how Konami, Sports Interactive and New Star Games have all shipped without licences. The project's name carries the same risk. Settle both before the first external TestFlight build, because Beta App Review is where these problems first become expensive.
